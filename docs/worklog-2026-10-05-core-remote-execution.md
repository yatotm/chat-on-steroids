# 单一 Core 的远程执行

后续：用户测试结束后已授权实施 RD-01～RD-05。这些修改及上游 `a8161d6` 适配已在 2.2.2 本地构建中实现并安装验收，详见[后续工作记录](worklog-2026-10-06-remote-hosts-upstream.md)。下列“尚未实现”“待统一更新”和手动 SSH 限制均保留为当时的历史记录，当前状态以后续记录为准。

用户确认将 CodexPro 与 CoS 完全分开。ChatGPT 的一条 CoS tunnel 连接 Mac Core；Mac 通过私有 SSH 转发调用 Linux 上的 CoS 执行服务，无需 Plugins 连接器或第二条 CoS tunnel。

## 实现

- 抽出原 Core 文件与命令处理器，在 Mac 和无界面的 Node 执行器中复用。构建检查禁止执行器引入 Electron、会话、队列、agents 等桌面权威模块。
- Mac 继续独占请求归属、权限、项目绑定、历史与编排。Linux 独占进程与输出；远程句柄包含服务身份和启动代际，不能跨项目或会话使用。断线不会切回本机，也不会自动重跑结果不明的命令。
- 后台输出沿用真实输出游标和发布回执。HTTP 断线撤销在途输出占用，即使失败 ACK 先于旧请求完成也不会留下孤立回执。关闭服务会等待已接受请求和正在启动的进程退出。
- 远程项目界面改为执行服务地址、令牌和目录；显式重连可保留旧项目身份。令牌通过已有加密凭据存储保存，项目目录只保存凭据引用。
- 移除远程项目对 Plugins 的要求，保留通用可选 Plugins 功能。文档说明独立隧道、SSH 转发、迁移和重启边界。

### 用户确定的交互

- **选择开发机**：在“连接设置 → 连接开发机”弹窗，通过下拉栏选择本机 `~/.ssh/config` 已配置的主机别名，复用已有 SSH 配置和认证方式。
- **一次提交完成连接**：选择主机和项目后，点击“连接并添加项目”，由 CoS 自动建立 SSH 端口映射、验证执行服务和目录，再保存项目并明确显示成功或失败。正常流程不要求用户额外打开终端运行转发命令。
- **每台开发机共享一条映射**：同一开发机的多个项目共用一条 SSH 转发和一个本机监听端口。重复点击、并发添加项目、刷新、重连也不能额外建立映射。不同开发机应正确分配端口，避免冲突。
- **项目列表分栏**：主界面的“项目”区域分别显示本地项目与远程开发机/项目。远程项目显示对应 SSH 主机名和实际连接状态，并提供刷新状态、重连入口；连接操作归属开发机，不能按项目重复建立转发。
- **软件关闭清理**：CoS 关闭/退出时关闭自己创建的全部 SSH 映射，释放对应端口。关闭窗口、后台驻留与真正退出的行为必须明确，不能留下用户未感知的后台映射。只清理 CoS 自己拥有的进程，不误停用户手动 SSH、CodexPro 或其他应用的连接。
- **异常与恢复**：覆盖盒盖、睡眠/唤醒、断网/网络恢复、SSH 中断、应用异常退出及再次启动；旧连接失效时撤下成功状态，恢复或重连时重新验证，不遗留占用、不重复开映射，也不自动重放结果不明的文件修改或命令。

### 现有缺口与验收重点

当前侧栏中的远程项目仅证明配置已保存；左下角连接状态属于 ChatGPT 公共 tunnel，不能用来表示 Linux 可用。当前重连弹窗成功后关闭，缺少持续可见的远端连接状态与单独检查入口。

后续应在真实 Mac 上验证：同一主机添加两个项目仅有一个监听端口；主机和项目状态一致且可刷新；断开或暂停执行服务时不误报可用；重连不要求重新添加项目或重复输入已保存的令牌；睡眠/离线后恢复正常；关闭软件后自建 SSH 进程及端口消失；再次启动可恢复使用，并且用户自行管理的其他连接始终不受影响。

主机身份归并、多个 SSH 别名及配置继承、端口分配、后台驻留与自动恢复的具体实现，在统一更新时结合现有所有权和生命周期核对。当前记录不是完成声明，不改变单一 Core、独立 CodexPro 和 Linux 执行服务的既定架构。

## 待办 RD-02：Core 成功后误报缺少 Plugins

**状态：已定位，待用户测试结束后统一修复。** 用户已经通过 Core 读取远程文件，界面仍提示尚未调用 Chat On Steroids Plugins、要求在 ChatGPT 创建。

源码原因：`mcp/surfaces.ts::surfaceIsUseful()` 对 Plugins 总是返回 true；`connection.ts::describeSurfaces()` 据此设置 available；`renderer/main.ts` 把所有 available 且从未请求的 surface 计入 unverified，没有按必需性、用户是否选择发布以及实际发布状态区分。连接器卡片已过滤 Plugins，但汇总告警仍包含它，形成相互矛盾的提示。关闭旧插件安装项并不保证修复这个恒真判断。

修复应在同一个连接器状态判定中区分“必需”“用户已选择并发布的可选功能”和“未启用的可选功能”。只有 Core 的远程开发配置必须能够完整通过；不应要求新增 Plugins tunnel 或连接器，也不能隐藏真正已配置连接器的失败。

## 待办 RD-03：纯远程项目被权限健康检查误判失败

**状态：已定位，待统一修复。** 用户的远程读取成功，但“连接健康”报告 `Permissions` 失败，详情为 `0 folders shared`，文件和命令权限均已开启。

源码原因：`diagnostics.ts::runDiagnostics()` 只用本机 `config.roots.length` 或 Desktop 能力判断权限可用，未考虑远程项目与执行服务。`connection.ts` 的连接准入已经允许纯远程项目，健康检查仍沿用旧的本地目录模型。

修复应分别呈现本地目录、远程工作区和执行权限，依据实际执行边界给出结论。纯远程项目不应为了消除红字而共享无关的 Mac 文件夹；同时，保存的项目配置不等于远端当前可访问，远端验证失败也不能仅靠存在项目记录变绿。

## 待办 RD-04：同主机新增项目重复要求令牌及目录创建入口

**状态：已定位当前限制，纳入 RD-01 的统一主机连接交互。** 用户尝试增加开发机目录，先被“执行服务访问令牌必填”阻挡。

当前 `remote-project-dialog.ts` 每次都新建必填令牌字段且不复用已有服务凭据，`projects.ts::addRemoteProject()` 接受完整凭据后再为项目创建凭据引用。令牌属于已配置的执行服务；正常新增同主机项目应选择已保存的连接并复用凭据，仅首次连接或主动更新凭据时要求输入。

当前“连接并添加项目”实际只绑定已存在且位于执行服务批准根目录内的目录，`executor/server.ts::workspace()` 调用 realpath/stat 检查，不创建目录。补足界面时应明确区分“添加已有目录”和“新建目录”，让目录不存在、超出批准范围、凭据问题分别给出可操作反馈；明确新目录的授权边界，不偷偷扩大到整台主机。用户随后明确允许父目录 `/root`，运行配置调整及验证见 RD-05；目录创建和新增项目交互仍待统一更新。

## 待办 RD-05：多个授权目录与主工作目录分离

**需求：用户需要通过条目添加多个远端读写授权目录，同时选择一个主项目目录进行开发。** 主目录决定默认工作位置与项目上下文；读写权限来自明确批准的目录列表，两者不能被同一个目录字段混为一谈。选择或关联项目目录本身不应偷偷扩大授权。多个目录仍复用同一台开发机的连接和凭据。

当前执行器 CLI 已支持多个 `--root`，但它们只限定能够选择哪些远程工作区。每次工具调用仍用 `ExecutionScope.directory` 同时作为 cwd 和唯一文件访问根，远程项目也没有附加目录能力。因此只扩大执行器启动参数不会让原有的单目录项目自动拥有跨目录文件访问能力。统一更新时需要把目录权限、主工作目录、项目关联以及 worker/接续的继承关系一起对齐，不能只改表单。

错误提示中的 `/root0`、`/root1` 是内部授权根别名，不是用户实际配置的目录。后续应提供可理解的已授权目录信息，明确错误发生在服务批准范围还是项目工作区边界。
